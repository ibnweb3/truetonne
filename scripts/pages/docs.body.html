Method, data and limits

What TrueTonne checks, how, and what it cannot tell you. Everything here is reproducible from the public repository.

What it checks

A company says it retired some tonnes of carbon credits. TrueTonne asks one narrow question: do public registry records show retirements that name this company, for those projects, vintages and years, in at least those quantities? It checks paperwork. It does not judge whether a project removes any carbon.

Data

  • CarbonPlan OffsetsDB, a compilation of the Verra, Gold Standard, ACR, CAR and ART registries. Snapshot of 1 June 2026: 495,403 retirements across 11,659 projects.
  • CarbonPlan has paused updates because registry data access changed (offsets-db-data#174). TrueTonne therefore cannot see retirements after the snapshot, and says so when a claim is dated later.
  • CarbonPlan claims no copyright in the data. The registries may claim rights in their own records; this site shows short extracts with a link to the registry.

Matching

  1. Project. By registry ID (VCS562, GS1234, CAR1480 and similar forms), or by name through full-text search. Name matches are flagged so you can confirm them.
  2. Claimant. A retirement counts only if the beneficiary, account or note field names the claimant (legal suffixes such as Inc or AB are ignored). The snapshot has no serial numbers, so matching is by project, vintage, retirement year and name, not by individual credit.
  3. Allocation. One retired tonne can back one claim within a report. If two claims in the same report match the same retirement, the second is shown as already counted.
  4. Flags. Retired more than issued; claimant is the account that retired on behalf of a client; claim dated after the snapshot; retirement matched only through a free-text note.

The AI step

Pasted text goes to Llama 3.3 70B on Cloudflare Workers AI, which only extracts claims into a fixed JSON shape. Any project ID, project name, tonnage or year that does not appear literally in your text is discarded and listed back to you. You review the claims before anything is checked. The model decides nothing about the verdict.

The on-chain record

Every report is canonical JSON hashed with SHA-256. You can re-hash it in your browser on the report page. Recording a report on Base Sepolia (a test network) calls TonneLedger, which keeps a cap in milli-tonnes per retirement row. The first claimant to record a row holds those tonnes; a later claimant asking for more than remains is refused and the contract logs a DoubleClaimBlocked event. Claimants are stored as the hash of their normalized name, not the name.

Only the server's attester key can write to the contract. This is a test-network demonstration of the mechanism, not a production registry.

Limits you should know

  • A retirement naming a company is evidence the credits were retired, not that the company's footprint is offset, and not that the project is good.
  • Registries record beneficiaries inconsistently. Many retirements name nobody, so an honest claim can show a gap.
  • The double-claim block only works between reports recorded on this contract. It does not see claims made anywhere else.
  • Name matching can confuse companies that share a name. The report shows every matched row so you can check.
